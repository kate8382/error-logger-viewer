# Настройка защиты веток (Branch Protection) в личном репозитории

Этот документ содержит пошаговую инструкцию по настройке правил защиты веток в GitHub для личного проекта с возможностью мерджить собственные Pull Request'ы.

## Зачем нужна защита веток?

Защита веток помогает:
- Предотвратить случайные изменения в важных ветках (main, master, production)
- Обеспечить прохождение тестов перед мерджем
- Требовать code review (в командных проектах)
- Сохранить историю изменений через Pull Request'ы

## Особенности личного репозитория vs организации

В **личных репозиториях** (не в организациях) владелец репозитория имеет особые привилегии:
- Владелец может мерджить свои собственные PR даже с включенной защитой веток
- Некоторые настройки защиты можно обходить (опционально)
- Не требуется дополнительных разрешений для команды

## Пошаговая инструкция

### Шаг 1: Перейдите в настройки репозитория

1. Откройте ваш репозиторий на GitHub
2. Нажмите на вкладку **Settings** (Настройки)
3. В левом меню найдите раздел **Branches** (Ветки)

### Шаг 2: Создайте правило защиты ветки

1. Нажмите кнопку **Add branch protection rule** (Добавить правило защиты ветки)
2. В поле **Branch name pattern** укажите имя ветки, которую хотите защитить:
   - `main` — для защиты главной ветки
   - `master` — если используете master
   - `production` — для продакшн-ветки
   - Можно использовать паттерны: `release/*`, `v*` и т.д.

### Шаг 3: Настройте правила (рекомендуемые для личного проекта)

#### Базовые настройки:

✅ **Require a pull request before merging**
- Включите эту опцию, чтобы все изменения проходили через PR
- **Внутри этой опции:**
  - ❌ **Require approvals** — можно **НЕ** включать для личного проекта
    - Если включите, потребуется указать количество аппрувов (обычно 1)
    - В личном репозитории вы можете аппрувить свои собственные PR
  - ✅ **Dismiss stale pull request approvals when new commits are pushed** — рекомендуется включить
  - ❌ **Require review from Code Owners** — не обязательно для личного проекта

✅ **Require status checks to pass before merging**
- Включите, если у вас есть CI/CD (например, GitHub Actions)
- Выберите конкретные проверки, которые должны пройти (например, `CI`, `tests`, `build`)
- **Внутри этой опции:**
  - ✅ **Require branches to be up to date before merging** — рекомендуется для избежания конфликтов

✅ **Require conversation resolution before merging**
- Включите, если хотите, чтобы все комментарии в PR были разрешены перед мерджем
- Полезно для самодисциплины и контроля качества

❌ **Require signed commits** — опционально
- Требует подписывать коммиты GPG ключом
- Повышает безопасность, но не обязательно для личного проекта

❌ **Require linear history** — опционально
- Запрещает merge commits, разрешает только rebase или squash
- Полезно для чистой истории

✅ **Require deployments to succeed before merging** — опционально
- Если у вас настроены deployment environments

#### Настройки обхода правил (важно для личного проекта):

⚠️ **Do not allow bypassing the above settings**
- **НЕ включайте** эту опцию, если хотите иметь возможность быстро мерджить свои PR в экстренных случаях
- Если **не отметите** эту галочку, вы как владелец сможете:
  - Мерджить PR без прохождения проверок (в экстренных случаях)
  - Пушить напрямую в защищенную ветку (если очень нужно)

❌ **Allow force pushes** — не рекомендуется
- Разрешает `git push --force`
- Может нарушить историю и работу других участников

❌ **Allow deletions** — не рекомендуется
- Разрешает удалять защищенную ветку

### Шаг 4: Дополнительные настройки (опционально)

**Rules applied to everyone including administrators:**
- ✅ **Require status checks to pass**
- ✅ **Require pull request reviews**
- Эти правила будут применяться даже к владельцу репозитория

**Lock branch** — не рекомендуется для активной разработки
- Делает ветку read-only
- Используется для архивных веток

### Шаг 5: Сохраните правило

Нажмите **Create** (Создать) или **Save changes** (Сохранить изменения)

## Пример конфигурации для личного проекта

Вот рекомендуемая конфигурация для активного личного проекта:

```
Branch name pattern: main

✅ Require a pull request before merging
   ❌ Require approvals: 0 (или 1, если хотите самодисциплину)
   ✅ Dismiss stale pull request approvals when new commits are pushed

✅ Require status checks to pass before merging
   ✅ Require branches to be up to date before merging
   Status checks: CI, build, tests (выберите свои)

✅ Require conversation resolution before merging

❌ Do not allow bypassing the above settings (НЕ отмечено!)
   → Это позволит вам обходить правила как владельцу

❌ Allow force pushes
❌ Allow deletions
```

## Как работать с защищенной веткой

### Обычный workflow:

1. **Создайте новую ветку** для своих изменений:
   ```bash
   git checkout -b feature/my-new-feature
   ```

2. **Внесите изменения и закоммитьте**:
   ```bash
   git add .
   git commit -m "Add new feature"
   ```

3. **Отправьте ветку на GitHub**:
   ```bash
   git push origin feature/my-new-feature
   ```

4. **Создайте Pull Request** на GitHub:
   - Перейдите в репозиторий на GitHub
   - Нажмите **Compare & pull request**
   - Заполните описание PR
   - Нажмите **Create pull request**

5. **Дождитесь прохождения проверок** (CI/CD):
   - GitHub Actions автоматически запустит тесты
   - Проверки должны пройти успешно (зеленая галочка)

6. **Мерджите PR**:
   - Нажмите **Merge pull request**
   - Выберите тип мерджа:
     - **Create a merge commit** — сохраняет всю историю
     - **Squash and merge** — объединяет все коммиты в один
     - **Rebase and merge** — применяет коммиты поверх main
   - Нажмите **Confirm merge**

7. **Удалите ветку** (опционально):
   - GitHub предложит удалить ветку после мерджа
   - Локально: `git branch -d feature/my-new-feature`

### Если нужно срочно смерджить (обход правил):

Как владелец репозитория, вы можете:

1. **Мерджить PR без прохождения проверок**:
   - Если проверки не прошли, но вы уверены в коде
   - Внизу PR будет кнопка **Merge without waiting for requirements to be met**
   - Нажмите её и подтвердите

2. **Пушить напрямую в main** (если правила позволяют):
   ```bash
   git checkout main
   git pull
   # внесите изменения
   git add .
   git commit -m "Hotfix: critical bug"
   git push origin main
   ```
   ⚠️ Используйте это только в экстренных случаях!

## Проверка настроек

После настройки проверьте, что всё работает:

1. Создайте тестовую ветку и PR
2. Убедитесь, что:
   - Нельзя пушить напрямую в `main` (если настроили строго)
   - CI/CD проверки запускаются автоматически
   - Можете смерджить PR после прохождения проверок
   - Можете обойти правила при необходимости (если не включили "Do not allow bypassing")

## Частые вопросы

### 1. Почему я не могу смерджить свой PR?

**Возможные причины:**
- Не прошли CI/CD проверки — дождитесь их завершения или исправьте ошибки
- Не разрешены комментарии — ответьте на все комментарии и отметьте их как resolved
- Ветка не обновлена — нажмите **Update branch** для синхронизации с main

### 2. Как временно отключить защиту ветки?

1. Settings → Branches → найдите правило
2. Нажмите **Edit** (карандаш)
3. Снимите нужные галочки или удалите правило
4. После завершения работы восстановите настройки

### 3. Можно ли защитить несколько веток?

Да! Создайте несколько правил с разными паттернами:
- `main` — главная ветка
- `develop` — ветка разработки
- `release/*` — все release-ветки
- `v*` — все версии

### 4. Влияет ли защита веток на GitHub Actions?

Нет, GitHub Actions может пушить в защищенные ветки используя `GITHUB_TOKEN`, если это настроено в workflow.

### 5. Нужно ли мне добавлять себя в Code Owners для личного проекта?

Нет, это не обязательно. Code Owners полезны в командных проектах для автоматического назначения ревьюеров.

## Резюме

Для личного проекта рекомендуется:
- ✅ Требовать Pull Request'ы для всех изменений
- ✅ Требовать прохождения CI/CD проверок
- ✅ Требовать разрешения всех комментариев
- ❌ **НЕ** включать "Do not allow bypassing" — это даст вам гибкость
- ❌ **НЕ** требовать обязательные аппрувы (или требовать 1 для самодисциплины)

Такая конфигурация обеспечит:
- Контроль качества через PR и CI/CD
- Возможность быстро реагировать на критические ситуации
- Чистую историю изменений
- Удобство работы в одиночку
